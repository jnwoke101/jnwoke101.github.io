Objective

Increase one target account balance to at least $1,000 in a controlled lab scenario.

Attack Idea

Send repeated transfer requests fast enough to exploit poor transaction handling.

Financial workflows need atomic transactions, locking, rate limits, and server-side validation.

Overview

In this lab, three bank accounts start with $100 each. The goal is to abuse a flawed transfer workflow so one account can receive more money than should be possible under normal transaction rules.

The key weakness is a race condition: the application processes multiple transfer requests close together without properly locking the account balance or validating each transaction as one atomic operation.

This writeup focuses on the security concept, the testing process, and the defensive lessons rather than encouraging misuse against real systems.

Business Impact

In a real financial application, this kind of bug could enable fraudulent transactions, duplicated transfers, inaccurate balances, financial loss, and loss of customer trust.

Walkthrough

Setup & Access

Opened Burp Suite's browser, authenticated to the lab application, and enabled Intercept to capture outgoing transfer requests.

Capture the Transfer Request

Identified the POST request responsible for money transfers, located it in HTTP history, and sent it to Repeater for controlled testing.

Exploit the Race Condition

Grouped and duplicated the transfer request in Repeater, then sent the requests in parallel to test whether the server handled concurrent balance updates safely.

Verify the Result

Logged back into the involved accounts to confirm the balance changes and validate that the race condition produced the intended CTF outcome.

Outcome

Result

Race Condition Confirmed

The lab successfully demonstrated how repeated near-simultaneous transfer requests can manipulate a vulnerable workflow and increase a recipient balance beyond expected limits.

Risk

Financial Logic Abuse

The vulnerability is not just a technical issue; it is a business logic failure that can directly impact revenue, trust, and fraud exposure.

Defensive Takeaways

Prevention

How to Fix This

  • • Use atomic database transactions for money movement.
  • • Apply row-level locking or safe concurrency controls during balance updates.
  • • Revalidate the sender balance server-side before each transaction commits.
  • • Add idempotency keys so repeated requests cannot duplicate the same action.

Detection

How to Monitor It

  • • Alert on repeated transfer requests from the same account in a short window.
  • • Monitor unusual balance changes or transaction spikes.
  • • Log request IDs, timestamps, session IDs, source IPs, and transaction states.
  • • Review fraud analytics for repeated small transfers or impossible balances.
