Scenario

The goal of this lab was to simulate safe PowerShell discovery behavior and validate whether Microsoft Sentinel could detect, alert, and support investigation of the activity.

The activity included local user discovery, local administrator group review, system information discovery, and process discovery from a Defender-onboarded Windows 11 lab VM. The investigation was performed as authorized lab activity, with sensitive identifiers redacted.

Detection Focus

Suspicious PowerShell command-line indicators, parent process context, account and host entity mapping, and MITRE ATT&CK discovery behavior.

Interactive Detection Workflow

Telemetry Validation

Controlled PowerShell Activity

Generated safe discovery commands including local user enumeration, administrator group review, system information discovery, and process review. No malware or unauthorized testing was performed.

Detection Engineering

Created a scheduled Sentinel analytics rule using KQL to detect suspicious PowerShell command-line indicators, then mapped host and account entities to improve triage quality.

SOC Investigation

Reviewed the Sentinel incident, process command line, parent process, account context, logon activity, MITRE mapping, and documented closure as authorized lab activity.

Detection Logic Highlights

PowerShell Indicators

Detected suspicious command-line strings such as -NoProfile, -ExecutionPolicy Bypass, and discovery cmdlets.

KQL Queries Used

Initial Hunt

Find PowerShell process activity

DeviceProcessEvents
| where TimeGenerated > ago(24h)
| where FileName in~ ("powershell.exe", "pwsh.exe")
| project
    TimeGenerated,
    DeviceName,
    AccountName,
    FileName,
    ProcessCommandLine,
    InitiatingProcessFileName,
    InitiatingProcessCommandLine
| order by TimeGenerated desc

Detection Rule

Suspicious PowerShell Discovery Activity

DeviceProcessEvents
| where TimeGenerated > ago(1h)
| where FileName in~ ("powershell.exe", "pwsh.exe")
| where ProcessCommandLine has_any (
    "-NoProfile",
    "-ExecutionPolicy Bypass",
    "Get-LocalUser",
    "Get-LocalGroupMember",
    "Get-ComputerInfo",
    "Get-Process"
)
| project
    TimeGenerated,
    DeviceName,
    AccountName,
    FileName,
    ProcessCommandLine,
    InitiatingProcessFileName,
    InitiatingProcessCommandLine

Context Review

Review logon activity around the event

DeviceLogonEvents
| where TimeGenerated > ago(24h)
| where DeviceName has "<DEVICE-NAME>"
| project
    TimeGenerated,
    DeviceName,
    AccountName,
    LogonType,
    ActionType,
    RemoteIP
| order by TimeGenerated desc

Related Events

Review supporting Defender events

DeviceEvents
| where TimeGenerated > ago(24h)
| where DeviceName has "<DEVICE-NAME>"
| project
    TimeGenerated,
    DeviceName,
    ActionType,
    AccountName,
    AdditionalFields
| order by TimeGenerated desc

Detection Tuning & Lessons Learned

Tuning

Reduce False Positives

The detection should be tuned by excluding approved administrator scripts, expected management tools, known maintenance activity, and trusted automation accounts. Higher-risk patterns such as encoded commands, hidden windows, download cradles, and unusual parent processes should receive higher priority.

Outcome

End-to-End SOC Workflow Practiced

This project connected detection engineering with SOC investigation by building the rule, validating the alert, reviewing the evidence, mapping behavior to MITRE ATT&CK, and documenting response recommendations.

Expandable Investigation Notes

PowerShell discovery commands can be used by administrators, but they are also commonly used by attackers after initial access to understand the host, accounts, privileges, and running processes.

The detection included command-line indicators, entity mapping, custom details, MITRE mapping, and investigation queries, making it more useful than a simple one-off log search.

Future versions can include watchlists, suppression logic, enrichment, parent process scoring, Logic App automation, and incident grouping based on host and account activity.
